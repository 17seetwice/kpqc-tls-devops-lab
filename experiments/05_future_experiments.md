# 후속 실험 설계

전환·성능 승인·자동 복구는 [후속 실험](devops/deployment-recovery/README.md)에서 완료했다. 초당 10회 고정 도착률의 제한된 부하로 판정과 복구 기능을 검증했으며 최대 용량 측정과 구분한다.

아래 본문은 최초 후속 설계다. 실제 수행한 범위는 다음과 같이 구분한다.

| 항목 | 현재 수행 범위 | 남은 확장 |
|---|---|---|
| 초기화·순서 영향 | 동일 EC2 쌍에서 cold/warm 10개 균형 블록 수행 ([결과](performance/process-reuse/README.md)) | 다른 시간대·인스턴스 쌍의 독립 반복 |
| 네트워크·HRR | MTU 1500/9001, 추가 왕복 지연 0/10/30 ms, HRR 유발/대조 수행 | 60 ms·손실·수신 측 지연·실제 WAN |
| 동시 부하 | 작업자 8개, 클라이언트 1/4/16개, 조건당 8초 × 3블록 수행 | 장시간·독립 부하 생성기·도착률 제어 |
| 부하 중 전환 | 최초 시험 실패 보존, 별도 재시험 24,504회 접속·오류 0회 완료 | 반복 전환·기존 연결 드레인·장애 롤백 |
| 인증서 체인 | 사용자 지정 범위에서 제외 | 별도 과제 |

[네트워크 및 부하 실험 방법](performance/network-and-load/METHODS.md)에 실제 실행 조건을 명시했다. 아래의 60초 × 5회 등 초기 제안값은 완료한 실험의 조건이 아니다.

## 1. 실행 시점과 초기화 영향 분리

**질문:** 프로세스 재사용 차이가 다른 시간대에도 유지되는가?

기존 EC2 (Elastic Compute Cloud) 두 대로 가능하다. cold/warm 순서를 블록별 무작위화하고 여러 시간대에 독립 실행한다. 먼저 5회 실행으로 분산과 소요 시간을 확인한 뒤 10회 이상으로 확대한다. 실행별 중앙값을 분석 단위로 사용하고, 반복 실행을 반영한 구간 추정을 제시한다. 동일 실행 안의 연결을 모두 독립 실험처럼 집계하지 않는다. 현재 결과의 신뢰도를 높이는 첫 번째 우선순위다.

## 2. 지연·MTU와 HRR

**질문:** 메시지 크기와 추가 왕복이 네트워크 조건에 따라 어떤 비용을 만드는가?

기존 두 대에서 전용 시험 경로에 지연을 주입하고 실제 RTT를 검증한다. 예비 조건은 추가 RTT 0/10/30/60 ms와 MTU (Maximum Transmission Unit) 1500/9001이다. 처음에는 손실 없이 지연과 MTU를 분리해 비교한다. 양방향에 지연을 적용할 때 합산 RTT를 확인한다. 관리용 SSH와 실험 트래픽을 분리하고 원복을 자동화한다.

HRR은 별도 요인으로 시험한다. 지원 그룹에는 목표 KEM을 포함하되 첫 key_share에는 넣지 않는 조건을 구현할 수 있는지 현재 포팅 API부터 확인한다. 공통 그룹을 제거해 접속 실패를 일으키는 시험으로 대체하지 않는다. 실제 HRR (HelloRetryRequest) 1회, 최종 협상 그룹, 검증 성공을 함께 확인한다. 기존 메시지 카운터와 패킷 수집은 서로 다른 계층의 바이트로 분리해 보고한다.

## 3. 동시 접속과 서버 비용

**클라이언트 연결 수와 EC2 수는 다르다.** 한 EC2에서 여러 작업자가 독립 연결을 생성할 수 있다. 시작은 서버 1대 + 부하 생성 클라이언트 1대, 총 2대면 된다. 현재 서버는 fork 후 waitpid로 기다리는 등 연결을 순차 처리하므로 먼저 고정 크기 작업자 풀 또는 이벤트 기반 동시 처리 구현이 필요하다.

예비 부하는 동시 연결 1/4/8/16/32/64로 증가시킨다. 각 조건은 준비 구간 이후 60초 측정 × 5회로 시작하고 성공·실패·타임아웃, 초당 완료 핸드셰이크, p50/p95, 양쪽 CPU (Central Processing Unit)·메모리를 기록한다. 초기에는 기준선과 그림 5의 네 PQC (Post-Quantum Cryptography) 구성을 사용하고 이후 확장한다. 세션 재개와 HTTP (Hypertext Transfer Protocol) 요청은 섞지 않는다.

클라이언트 CPU/네트워크가 포화하거나 작업 스케줄 지연이 증가하면 클라이언트를 2대, 필요하면 4대로 늘린다. 따라서 총 EC2는 우선 2대, 확장 시 3–5대다. 클라이언트 추가 시 달성 부하가 증가하는지도 확인하여 서버 병목과 생성기 병목을 구분한다. 고정 동시 연결 시험은 부하가 느려질수록 요청 발생률도 낮아지므로 실제 도착률 모델을 대표하지 않는다. 용량 주장은 별도의 도착률 제어 시험으로 보완한다.

서버 비용은 안정적 처리량을 확보한 뒤에만 계산한다. 예를 들어 `서버 시간당 비용 / (성공 핸드셰이크/초 × 3600)`을 연결당 인스턴스 비용으로 정의하고 실패율·지연 목표·이용률을 함께 보고한다. 현재 단일 연결 지연만으로 필요한 서버 수나 비용 절감률을 계산하지 않는다. 실제 가격은 실행 당시 리전 가격으로 확인한다.

## 4. 부하 중 배포 전환

3번 부하 생성기를 재사용한다. 정상 후보 승격·정책 위반 후보 거절·후보 정리를 반복하고 연속적인 연결 결과를 수집한다. 전환 요청/완료 시각, 새 연결 실패율, 기존 연결 종료 여부, 최대 실패 연속 구간을 기록한다. 기존 69개 표본을 보완하는 실험이다. 연결 드레인과 롤백 동작을 먼저 정의해야 한다.

## 5. 인증서 체인 및 실제 서비스

리프–중간 CA–루트 구조를 만들고 체인 검증·인증서 크기·서명 혼합 정책을 평가할 수 있다. 먼저 현재 KPQC 이미지의 체인 발급·검증 기능을 확인한다. 자체 신뢰 리프 결과와 별도 실험으로 둔다. 새 인스턴스가 반드시 필요하지는 않다.

nginx/Envoy 등 실서비스 연동, 세션 재개 정책, 장기 드리프트 관측은 별도 확장 과제다. 라이브러리 연동 및 정책 의미를 먼저 설계해야 하므로 즉시 모든 항목을 추가하지 않는다. 관측 가능한 TLS (Transport Layer Security) 동작을 검증한다.

권장 진행 순서는 **반복 설계 개선 → 네트워크 조건 → 동시 부하 → 부하 중 전환**이다. HRR과 인증서 체인은 기능 지원 확인 후 독립된 소규모 실험으로 추가할 수 있다.
