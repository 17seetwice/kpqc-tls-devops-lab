# 실험 과정과 분석 방법

## 성능 실험

1. 서버·클라이언트 EC2에서 실험 이미지와 설정을 준비하고 이미지 식별 정보를 기록한다.
2. 기준선 1개와 KEM 7개 × 서명 6개, 총 43개 구성을 만든다.
3. 모드별 5라운드를 수행한다. 각 라운드 안에서 구성 순서를 무작위화하고, 앞뒤에 기준선 감시 측정을 둔다.
4. 새 프로세스 조건은 구성·라운드별 3회, 재사용 조건은 준비 연결 2회 후 분석 연결 3회를 수행한다.
5. TCP 연결과 준비 신호 이후, 클라이언트의 `SSL_connect` 시작부터 반환까지 모노토닉 시계로 측정한다. HTTP 수신·파일 전송·연결 종료 시간은 포함하지 않는다.
6. TLS 버전, cipher, 실제 그룹·서명 식별자, 인증서 검증 결과, 세션 재개와 HRR 여부를 기록한다. 양 끝의 방향별 핸드셰이크 메시지 바이트도 대조한다.

시간 분석은 모드·구성별 15회이다. 주 그림의 점은 15회 중앙값이고, 라운드 그림의 점은 해당 라운드 3회 중앙값이다. 라운드는 동일 EC2 실행 안의 반복이다. 메시지 바이트는 TLS 레코드·TCP/IP 헤더와 재전송을 포함한 회선 바이트가 아니다.

## 메모리 실험

시간 실험과 별도로 새 프로세스 조건에서 구성별 3회 측정한다. 초기화가 끝난 후 Linux `clear_refs=5`로 프로세스 RSS 최고 기록을 재설정하고, SSL 호출 구간에서 새롭게 높아진 최대 RSS를 계산한다. 양 EC2에서 16 MiB 버퍼 할당·페이지 접근 시 16 MiB 증가가 관측되는 사전시험을 수행했다.

지표 이름은 **핸드셰이크 구간 최대 RSS 증가량**이다. 이는 프로세스가 점유한 실제 메모리 페이지 증가를 관측하며, 알고리즘의 총 메모리 요구량이나 malloc 누적 할당량을 뜻하지 않는다. 기존 페이지 재사용, 파일 페이지 접근, 페이지 단위 계측의 영향을 받는다. n=3의 탐색적 관측으로 제시한다.

## 배포 검증

활성 서비스는 현재 트래픽을 받는 버전, 후보 서비스는 활성화 전에 검사할 새 버전이다. 후보에 대한 정상 연결뿐 아니라 고전 KEM 전용·고전 서명 전용·TLS 1.2 등의 제한된 프로브로 허용 범위를 검사한다. TLS 1.2 프로브는 별도 양성 대조로 동작을 확인한다.

정책은 승인된 TLS 버전·암호 조합, 인증서 검증, 금지된 접속의 거절, 후보와 증적의 일치 및 신선도를 확인한다. 혼합 설정에서 정상 PQC 접속이 성공하더라도 금지된 고전 접속까지 성공하면 후보를 거절한다. Provider 설치 여부는 정책에 넣지 않는다.

통과한 후보로 TCP 라우터의 활성 경로를 전환한다. 거절하면 기존 경로를 유지한다. 후보 세대·인증서·이미지·정책 식별자가 다른 증적, 오래된 증적, 타임아웃과 손상된 출력도 시험한다. 제어기는 신뢰한다고 가정한다.
