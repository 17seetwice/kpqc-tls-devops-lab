# KPQC TLS 성능 측정과 정책 기반 배포·복구 실험

랩미팅 자료 · 실험 목적·설계·환경·방법·결과

## 1. 실험 목적과 범위

본 실험은 **제한된 컴퓨팅 자원에서 KPQC TLS의 핸드셰이크 성능을 측정하고, 실제 암호 설정과 응답 성능에 따라 배포를 승인·거절하며, 배포 후 장애가 발생하면 이전 승인 KPQC 서비스로 복구하는 과정**을 검증한다.

사용자 제작 `dmfive/kpqc-ossl3` Docker 이미지의 OpenSSL을 사용한다. 성능 측정 대상은 SMAUG·NTRU+ 키 교환과 HAETAE·AIMer 서버 인증 서명이다. 고전 기준선은 X25519 + ECDSA P-256이며, 전환·성능 승인·복구 실험의 승인 조합은 SMAUG1 + HAETAE2다.

검증 범위는 다음과 같다.

- **성능 측정:** 암호 구성, 프로세스 준비 상태, 네트워크 조건과 동시 접속 수에 따른 TLS 지연·자원 사용·처리량.
- **배포 판단:** 실제 협상과 인증서 검증, 금지된 접속 거절, 응답 시간·성공률 기준 충족 여부.
- **장애 복구:** 신규 배포 서비스 중단 후 이전 승인 서비스 확인과 경로 복구.
- **실행 자동화:** GitHub Actions를 통한 이미지 빌드·시험·AWS 실행·증적 수집·자원 정리.

기반 이미지는 digest로 고정하고, AWS에 전달한 실제 이미지의 식별자를 대조한다. 각 실행의 소스 커밋과 원기록을 함께 보존한다.

## 2. 검증 질문과 구체적인 시험 상황

핵심 질문은 **“KPQC TLS가 동작하는 것을 넘어, 새 서비스를 배포할 수 있는 암호·성능 조건을 만족하는가?”**이다. 다음 표는 이를 확인하기 위한 시험 상황과 방법을 정리한다.

표의 예시는 각 문제를 이해하기 위한 시험 상황이다. 실제 측정 수치는 뒤의 실험별 결과에서 제시한다.

| 무엇이 궁금했는가? | 구체적으로 어떤 상황인가? | 어떻게 확인했는가? |
|---|---|---|
| **암호 구성에 따라 TLS 핸드셰이크 시간이 얼마나 다른가?** | 같은 서버·클라이언트에서 X25519 + ECDSA P-256과 SMAUG1 + HAETAE2를 비교한다. 프로그램 준비나 TCP 연결 시간을 섞으면 TLS 호출 구간의 차이를 구분하기 어렵다. | 같은 측정 경계로 `SSL_connect` 직전부터 반환 직후까지 기록하고, 구성별로 반복 측정했다. |
| **프로그램을 처음 실행했을 때와 계속 켜 둔 상태에서 연결할 때 속도가 다른가?** | 같은 SMAUG1 + HAETAE2라도, 매번 프로그램과 설정을 새로 준비하는 경우와 같은 프로그램의 설정을 유지하며 새 연결을 반복하는 경우가 있다. | 새 프로세스 조건과 프로세스 재사용 조건을 비교했다. 두 조건 모두 매번 전체 TLS 핸드셰이크를 수행했다. |
| **항상 나중에 측정한 조건이 유리하거나 불리해질 수 있지 않을까?** | 새 프로세스 조건을 전부 측정한 뒤 재사용 조건을 측정하면, 그동안 CPU·캐시·시스템 부하 상태가 달라질 수 있다. 시간 차이가 프로그램 재사용 때문인지 측정 시점 때문인지 구분하기 어렵다. | 후속 실험에서 새 프로세스를 먼저 실행하는 블록 5개와 재사용을 먼저 실행하는 블록 5개를 섞었다. 암호 구성의 시험 순서도 무작위로 배치했다. |
| **KPQC 연결이 성공해도, 허용하면 안 되는 고전 암호 연결이 함께 열려 있지는 않은가?** | 정책은 “SMAUG1만 허용”인데 업데이트 후 “SMAUG1과 X25519 모두 허용”으로 바뀔 수 있다. SMAUG1 접속만 시험하면 이 잘못된 설정을 놓친다. 이런 의도치 않은 설정 변경을 여기서는 **설정 회귀**라고 부른다. | 실제 SMAUG1 협상을 확인하고, X25519만 사용하는 시험 클라이언트는 거절되는지도 확인했다. 금지한 접속까지 성공하면 후보 배포를 거절했다. |
| **같은 암호 조합도 네트워크 환경이 달라지면 느려지는가?** | 같은 SMAUG1 + AIMer128f 연결이라도 한 패킷에 담을 수 있는 크기가 작거나 메시지 왕복이 느리면 시간이 달라질 수 있다. 서버가 필요한 키 교환 자료를 다시 요청하는 HRR도 추가 왕복을 만든다. | MTU (Maximum Transmission Unit) 1500/9001, 추가 왕복 지연 0/10/30ms, HRR (HelloRetryRequest) 발생·미발생 조건을 각각 비교했다. |
| **한 명씩 접속할 때의 성능이 여러 명이 동시에 접속할 때도 유지되는가?** | 시험 클라이언트 한 개가 접속을 반복할 때와 16개가 동시에 반복할 때는 서버가 처리해야 할 양이 다르다. 한 연결의 시간만으로 초당 처리 가능한 연결 수를 알 수는 없다. | 서버 작업자 8개와 클라이언트 프로세스 1·4·16개 조건에서 지연과 초당 완료 연결 수를 측정했다. 클라이언트 수는 EC2 대수가 아니라 한 EC2 안의 프로세스 수다. |
| **암호 설정은 맞지만 응답이 너무 느린 새 서비스를 배포해도 되는가?** | 인증서도 정상이고 SMAUG1 + HAETAE2 연결도 성공하지만, 서버가 처리를 350ms 늦춘다면 미리 정한 200ms 완료 목표를 넘길 수 있다. | 초당 10회씩 접속을 예약해 실패율·기한 내 성공률·지연을 검사했다. 연결 성공 여부와 별개로 성능 기준을 만족하지 못한 후보는 거절했다. |
| **새 서비스를 배포한 뒤 서버가 죽으면, KPQC를 유지하면서 되돌릴 수 있는가?** | 새 인증서와 서버 프로세스로 업데이트한 뒤 해당 프로세스를 중단한다. 이전에 승인된 KPQC 서비스가 살아 있다면 그쪽으로 새 연결을 보내 복구할 수 있어야 한다. | 연속된 접속 실패로 장애를 감지하고, 이전 서비스의 현재 연결·인증서·암호 설정을 다시 확인한 뒤 경로를 복구했다. 감지·복구 시간과 실패한 접속 수를 기록했다. |

예를 들어 **“실제 협상과 금지된 접속 시험을 결합한다”**는 다음 두 가지를 모두 검사한다는 뜻이다.

1. **되어야 하는 연결:** SMAUG1 + HAETAE2를 사용하는 클라이언트가 정상적으로 접속한다.
2. **막혀야 하는 연결:** 고전 키 교환만 제시하는 클라이언트는 접속하지 못한다.

둘 중 하나만 확인하면 부족하다. 정상 KPQC 접속만 성공하는지 보면 고전 암호 허용을 놓칠 수 있고, 고전 접속이 실패하는지만 보면 서버가 아예 꺼져 있는 경우도 정상으로 오해할 수 있다.

최종 질문은 **“정해진 CPU·메모리 한도에서 승인한 암호 설정과 응답 시간 기준을 만족하는 새 서비스만 배포하고, 장애가 나면 이전에 승인한 KPQC 서비스로 복구할 수 있는가?”**이다.

## 3. 전체 실험 절차

성능 측정과 배포·복구 시험은 목적에 맞게 구분해 수행하고, 결과는 실행별로 집계한다.

| 단계 | 수행 내용 | 확인할 결과 |
|---|---|---|
| 1. 환경 준비 | 서버·클라이언트에 동일 이미지를 준비하고 CPU·메모리 한도, 인증서와 신뢰 기준을 설정한다. | 실행 환경과 이미지 식별자 일치 |
| 2. 구성별 성능 측정 | 42개 KPQC 구성과 고전 기준선으로 전체 TLS 핸드셰이크를 반복한다. | 지연·CPU 시간·별도 메모리 지표 및 실제 협상 결과 |
| 3. 조건 변화 측정 | 대표 조합에서 MTU·왕복 지연·HRR·동시 접속 수를 바꾼다. | 조건별 지연과 완료 연결 수 변화 |
| 4. 암호 정책 검사 | 정상 후보와 잘못된 암호 설정·인증서·증적을 가진 후보를 검사한다. | 정상 후보 승인, 정책 위반 후보 거절 |
| 5. 성능 기반 승인 | 고정 도착률로 접속을 보내 정상 후보와 지연 주입 후보를 검사한다. | 연결 성공과 성능 기준 충족을 구분한 배포 판단 |
| 6. 전환 및 업데이트 | 승인된 KPQC 서비스로 전환하고, 동일 암호 조합의 새 인증서·프로세스로 업데이트한다. | 활성 경로와 실제 서버 인증서의 변경 |
| 7. 장애 복구 | 신규 서비스 중단 후 이전 승인 서비스의 현재 정상 여부를 확인하고 경로를 복구한다. | 감지·복구 시간, 실패 접속 수, 복구 후 암호 정책 유지 |
| 8. 증적 저장·정리 | 원자료·판정·소스·이미지 정보를 저장하고 EC2를 중지한다. | 결과 추적 가능성과 정리 완료 |

C 시험 프로그램은 실제 TLS 연결을 수행하고 계측한다. Python 제어 코드는 구성·반복 순서를 정하고 결과를 수집하며, 정책 코드는 배포 승인·거절을 판정한다. GitHub Actions는 이 절차를 실행하고 AWS 자원을 정리한다.

## 4. 공통 환경과 시스템 구조

| 항목 | 구성과 이유 |
|---|---|
| 암호 실행 환경 | 사용자 제작 KPQC–OpenSSL 이미지 기반 컨테이너. 양 끝에서 동일 구현 사용 |
| 클라우드 | AWS (Amazon Web Services) 서울 리전, 동일 가용 영역 `ap-northeast-2a` |
| 인스턴스 | m7i.large 서버 1대, 클라이언트 1대 |
| 자원 제한 | 각 실험 컨테이너에 CPU 2개와 메모리 512 MiB 한도 적용 |
| 실험 통신 | 두 EC2 (Elastic Compute Cloud)의 사설 IPv4 사이 TLS 연결 |
| 관리 통신 | GitHub runner 또는 로컬 제어기에서 SSH (Secure Shell)로 실행 제어 |
| TLS | TLS (Transport Layer Security) 1.3, `TLS_AES_256_GCM_SHA384` |
| 인증서 | 직접 신뢰한 서버 리프 인증서, 이름 및 검증 결과 확인 |
| 기준선 | X25519 키 교환 + ECDSA P-256 서버 인증 |
| KPQC 대상 | KEM 두 계열 SMAUG·NTRU+, 서명 두 계열 HAETAE·AIMer |
| 초기 네트워크 | Docker host network, 관측된 NIC MTU 9001 |
| 후속 네트워크 | Docker bridge에서 MTU 1500/9001 비교. 최종 전환·복구는 MTU 1500 |

MTU (Maximum Transmission Unit)는 한 번에 전달할 수 있는 네트워크 계층 패킷의 최대 크기다. 초기 9001은 기존 인터페이스의 관측값이고, 성능을 높이려고 처음부터 1500을 늘린 것이 아니다. 후속 비교에서는 같은 브리지 방식 안에서 MTU만 바꿨다.

CPU와 메모리 **한도**는 환경이고, 실제 사용 CPU 시간과 RSS는 **측정 결과**다. 512 MiB를 설정했다고 연결 하나가 512 MiB를 사용한 것은 아니다.

동시 클라이언트 16개는 EC2 16대가 아니라 클라이언트 EC2 한 대 안의 프로세스 16개다. 3,600개 연결 역시 인스턴스 3,600대가 아니다.

성능 측정은 서버에 직접 연결한다. 배포 시험에서는 실험용 TCP (Transmission Control Protocol) 라우터가 활성 서비스 또는 후보 서비스로 연결을 전달한다. 이 라우터는 배포 경로 전환을 모사하는 도구이며, 운영용 로드밸런서 전체를 구현한 것은 아니다.

### 인증서와 개인키의 보관

서버 인증서와 개인키는 각 실행의 준비 단계에서 생성한다. 개인키는 서버 컨테이너의 `/state` 경로에 암호화하지 않은 PEM 파일로 저장하며, 이 경로는 `tmpfs`로 마운트한다. 개인키를 이미지에 포함하거나 클라이언트의 신뢰 자료로 전달하지 않는다. 클라이언트에는 공개 인증서만 배포한다. 최종 전환·복구 실험은 종료 처리에서 서버·클라이언트 컨테이너를 제거하므로 해당 임시 파일도 함께 제거된다.

Vault·AWS Secrets Manager·HSM (Hardware Security Module) 같은 별도 키 보관 시스템, 운영 키 회전 및 접근 감사는 구현하지 않았다. `tmpfs` 사용과 컨테이너 정리는 시험 키의 수명 관리 방식이며, 호스트 관리자 접근이나 스왑 등을 포함한 운영 키 보호를 입증하는 것은 아니다. 개인키 파일의 실행 시 권한 검증도 별도 증적으로 수집하지 않았다.

### 라우터와 상태 확인의 역할

실험용 TCP 라우터는 연결 시작 시 활성·후보·복구 대상 중 하나를 선택하고, TLS를 종료하거나 복호화하지 않은 채 해당 서버 프로세스로 바이트를 전달한다. 활성 경로 변경은 이후 새로 수락하는 연결의 대상에 반영된다. 이미 중계 중인 연결을 다른 서버로 옮기는 기능은 없다.

상태 확인과 승인·복구 판단은 라우터가 아니라 별도 제어 코드가 실제 TLS 접속 시험으로 수행한다. 기존 연결이 끝날 때까지 기다린 뒤 이전 서버를 제거하는 연결 드레이닝 절차는 구현·검증하지 않았다. 따라서 이 실험은 ALB (Application Load Balancer)·NLB (Network Load Balancer)의 상태 확인·트래픽 분산·드레이닝을 재현한 시험이 아니라, 정책 판단에 따른 새 연결의 경로 전환 시험이다.

## 5. 측정 지표와 구간

| 지표 | 측정 방법 | 설명할 수 있는 것 |
|---|---|---|
| TLS 핸드셰이크 지연 | 클라이언트 `SSL_connect` 직전·직후 단조 시계 차이 | 클라이언트가 관측한 전체 TLS 핸드셰이크 경과 시간 |
| 서버·클라이언트 CPU 시간 | 해당 SSL 호출 전후 사용자+커널 CPU 시간 차이 | 그 프로세스가 호출 구간에 사용한 CPU 시간 |
| 핸드셰이크 구간 최대 RSS 증가 | 초기화 후 최고 RSS 기록 재설정, 호출 후 최고 기록과 차이 계산 | 구간 내 새롭게 증가한 상주 메모리 최고 기록 |
| 핸드셰이크 메시지 바이트 | OpenSSL 메시지 콜백에서 송수신 길이 집계 | TLS 핸드셰이크 메시지 크기 |
| 처리량 | 성공한 연결 수 / 실제 부하 실행 시간 | 계측용 서비스·클라이언트 조합의 완료 연결/초 |
| 배포 성능 검사 완료 시간 | 접속 예정 시각부터 시험 클라이언트 종료까지 | 예정된 요청이 기한 내 완료되는지 |
| 감지·복구 시간 | 장애 주입 요청부터 감지 및 첫 복구 성공 확인까지 | 제어기 관점의 자동 복구 소요 시간 |

시험 프로그램은 TLS 호출 전에 평문 1바이트 준비 신호를 교환하며, 배포 시험에서는 경로 선택 문자열도 전달한다. 이 시험용 정보는 TLS 표준 메시지가 아니며 `SSL_connect` 시간에서 제외된다. 따라서 해당 접속 절차는 일반 HTTPS 클라이언트와 직접 호환되는 서비스 인터페이스가 아니다.

단조 시계는 경과 시간을 측정하기 위한 시계다. CPU 시간은 벽시계 경과 시간과 달라서 네트워크를 기다린 시간 전체가 CPU 시간으로 잡히지 않는다.

RSS (Resident Set Size)는 프로세스의 물리 메모리 상주량이다. 측정 전 Linux `clear_refs=5`로 최고 기록을 재설정하고 `VmHWM`의 증가를 읽었다. 기존 페이지 재사용과 코드·스택 접근 등이 영향을 주므로 서명 크기와 일대일로 대응하지 않는다. 시간 측정과 메모리 측정은 별도 실행했다. 16 MiB 페이지 접근 양성 대조를 양쪽에서 수행했으나 작은 차이의 정밀도 검증은 별도 과제로 남아 있다.

메시지 콜백은 OpenSSL이 메시지를 처리할 때 호출하는 관찰 함수다. 여기서 센 바이트에는 전체 Ethernet/TCP/IP 헤더와 재전송 바이트가 포함되지 않는다.

두 가지 지연을 반드시 구분한다. **암호 성능 그림은 `SSL_connect` 호출 시간**, **배포 성능 게이트는 접속 예정 시각부터 클라이언트 종료까지**다. 후자는 스케줄 대기·초기화·TCP·TLS·종료를 포함한다. 같은 수치로 비교하지 않는다.

## 6. 실험 1: 암호 구성별 핸드셰이크 비용

### 구성과 절차

KEM은 SMAUG 1/3/5와 NTRU+ 576/768/864/1152의 7개, 서명은 HAETAE 2/3/5와 AIMer 128f/192f/256f의 6개다. 7×6=42개 KPQC 구성에 고전 기준선 1개를 더해 43개를 시험했다. 여러 보안 파라미터의 관측이며 동일 보안 수준의 알고리즘 순위표로 해석하지 않는다.

- **새 프로세스 조건(cold)**: 클라이언트는 연결마다 새 프로그램을 실행하고, 서버는 연결마다 새 자식 프로세스를 생성하여 TLS 컨텍스트를 준비한다. 운영체제 캐시를 강제로 비우는 실험은 아니다.
- **프로세스 재사용 조건(warm)**: 프로세스와 OpenSSL 컨텍스트를 유지하고 준비 연결 후 분석한다. 매번 새 연결과 전체 핸드셰이크를 수행한다.
- **세션 재개(resumption)**: 이전 연결의 상태를 이용해 핸드셰이크를 줄이는 기능이다. 이번 비교에서는 제외했으므로 warm과 세션 재개는 다르다.

초기 실험은 5라운드 × 구성·모드별 3회로 시간 분석 1,290회였다. 별도 메모리 분석은 43개 구성 × 3회=129회였다. 준비·감시 516회를 포함한 총 수집은 1,935회다.

이후 cold를 항상 먼저 실행한 설계의 한계를 발견해 10개 블록 중 cold-first 5개, warm-first 5개로 균형을 맞췄다. 블록 안의 암호 구성 순서는 무작위화했고, 두 모드에서 같은 구성 순서를 사용했다. 후속 수집은 3,600회, 시간 분석은 구성·모드별 30회로 총 2,580회였다. 나머지 1,020회는 준비·감시 연결이다.

|---|---|---:|---:|
| 초기 실행 | 새 프로세스 | 1.388 ms | 3.503–11.287 ms |
| 초기 실행 | 프로세스 재사용 | 0.538 ms | 2.403–10.529 ms |
| 순서 균형화 후속 실행 | 새 프로세스 | 1.724 ms | 3.891–12.218 ms |
| 순서 균형화 후속 실행 | 프로세스 재사용 | 0.815 ms | 2.852–11.500 ms |

범위는 **구성별 중앙값 중 가장 작은 값과 큰 값**이다. 전체 개별 연결의 최솟값·최댓값이 아니다. 서로 다른 실행의 값을 합치지 않았다.

후속 실행의 전체 표본 중앙값은 43개 구성 모두 재사용 조건에서 낮았다. 다만 일부 차이는 작았고 모든 블록·시작 순서에서 항상 빨랐던 것은 아니다. 따라서 초기화·실행 조건을 구분해서 측정해야 한다는 결과로 설명한다.

초기 별도 메모리 실행에서 KPQC 구성별 중앙값 범위는 클라이언트 648–980 KiB, 서버 628–1,252 KiB였고, 기준선은 460/420 KiB였다. 이는 구간 최대 RSS 증가량이며 총 메모리 요구량이 아니다. 후속 순서 균형화 실행은 메모리를 다시 측정하지 않았다.

CPU와 메시지 바이트도 원기록에 남겼다. 본 설명에서 수치를 생략한 지표를 미측정으로 뜻하지는 않는다. 상세 값은 [초기 집계 CSV](../../experiments/data/summary.csv)와 원기록을 확인한다.

## 7. 실험 2: 실제 협상에 근거한 암호 정책 게이트

정책은 “KPQC이면 무엇이든 허용”이 아니라 승인된 **TLS 1.3 + SMAUG1 + HAETAE2 + TLS_AES_256_GCM_SHA384** 조합을 요구한다. 다른 KPQC 조합을 쓰려면 정책도 변경해야 한다.

TLS 1.3 cipher suite는 대칭키 암호와 해시 구성을 나타낸다. KEM 그룹과 인증 서명은 별도 항목으로 확인한다. 따라서 cipher suite 문자열만 보고 SMAUG나 HAETAE가 사용됐다고 판단하지 않는다.

잘못된 KEM·서명과 인증서 지문이 다른 증적, 그리고 KPQC와 고전 암호를 동시에 허용하는 혼합 설정을 검사했다. 예를 들어 서버가 SMAUG와 X25519를 모두 허용하면 정상 KPQC 클라이언트는 성공할 수 있다. 이때 X25519 전용 클라이언트도 성공한다면, 고전 접속 금지 정책 위반을 검출해야 한다.

| 시험 입력 | 기대하는 게이트 동작 |
|---|---|
| 정상 KPQC 후보 | 승인 |
| 고전 KEM 또는 고전 서명 후보 | 거절 |
| KPQC와 고전 접속을 동시에 허용 | 고전 전용 프로브 성공을 확인하고 거절 |
| TLS 1.2 전용 접속 | 거절. 별도 양성 대조로 시험 클라이언트 자체가 정상인지 확인 |
| 후보·인증서·이미지·정책 불일치 | 거절 |
| 오래된 결과, 타임아웃, 손상된 결과 | 거절 |

정상 연결에서는 인증서 검증 성공도 요구한다. 현재 63개 검증 항목에 포함된 인증서 부정 시험은 증적의 인증서 지문을 바꾸는 시험이다. 실제 잘못된 이름·만료·신뢰 체인 인증서를 각각 배포한 시험과는 구분한다.

판정 자료는 어느 후보에 대한 결과인지 식별하고 신선도를 검사한다. 이는 신뢰하는 제어기의 실수나 과거 결과 재사용을 탐지하기 위한 장치다.

최종 기존 게이트는 로컬과 AWS에서 각각 63개 검증 항목을 통과했다. **63은 TLS 연결 수가 아니라 검증 항목 수**다. 잘못된 후보를 예상대로 거절하는 것도 통과다.

이 단계의 의미는 실제 관측된 암호 설정을 배포 조건으로 연결한 것이다. 암호 구현의 로딩 방식은 정책 조건으로 두지 않았다.

## 8. 실험 3: 네트워크·추가 왕복·동시 부하

전체 43개 대신 고전 기준선과 {SMAUG1, NTRU+ KEM768} × {HAETAE2, AIMer128f}의 대표 5개 조합을 사용했다.

### MTU와 네트워크 지연

같은 Docker 브리지 구성에서 MTU 1500/9001, 설정상 추가 왕복 지연 0/10/30 ms를 비교했다. 양 끝의 송신에 각각 0/5/15 ms를 주입했다. 실제 인터넷 경로가 아니라 통제된 지연 조건이다.

추가 왕복 지연 30 ms에서 관측한 대표 결과다. 각 값은 세 블록에서 구한 핸드셰이크 지연 중앙값의 중앙값이다.

| 구성 | MTU 1500 | MTU 9001 |
|---|---:|---:|
| X25519 + ECDSA P-256 | 31.322 ms | 31.271 ms |
| SMAUG1 + HAETAE2 | 33.766 ms | 33.609 ms |
| SMAUG1 + AIMer128f | 62.576 ms | 34.128 ms |
| NTRU+ KEM768 + HAETAE2 | 33.906 ms | 33.994 ms |
| NTRU+ KEM768 + AIMer128f | 62.886 ms | 34.350 ms |

특정 구성에서 작은 MTU와 지연이 결합될 때 큰 차이가 나타났다. 암호 연산뿐 아니라 전송 조건도 TLS 지연을 좌우한다는 관측이다. 패킷 수준의 원인 분석 없이 특정 TCP 동작 하나가 원인이라고 확정하지 않는다.

### HRR 추가 왕복

HRR (HelloRetryRequest)은 서버가 필요한 키 교환 자료를 다시 요청하는 메시지다. 공통으로 지원하는 그룹은 있지만 첫 ClientHello에 필요한 키 공유가 없도록 구성해 HRR을 유발했다. 대조군과 최종 암호 조합은 동일하게 유지했다.

HRR 유발 180회는 각 1회, 대조 180회는 각 0회를 관측했다. 준비 연결을 제외한 분석은 216회다. 같은 블록의 HRR 조건과 대조 조건 사이 지연 중앙값 차이를 구한 뒤 세 블록의 중앙값으로 집계했다. 설정상 추가 왕복 지연 30 ms에서 HRR로 늘어난 지연은 구성별 약 30.858–31.291 ms였다. 추가 왕복 비용이 관측 지연에 반영됐다.

### 동시 접속과 처리량

서버를 작업자 프로세스 8개가 연결을 처리하는 구조로 바꾸고, 클라이언트 프로세스 1/4/16개가 접속을 반복하도록 했다. 각 조건은 8초 × 3블록이다. 총 273,091개 연결의 협상과 인증서 검증을 확인했다.

| 구성 | 클라이언트 1개 | 4개 | 16개 |
|---|---:|---:|---:|
| X25519 + ECDSA P-256 | 1,232.7 | 2,430.3 | 2,596.2 |
| SMAUG1 + HAETAE2 | 288.9 | 532.8 | 571.5 |
| SMAUG1 + AIMer128f | 279.1 | 471.5 | 556.1 |
| NTRU+ KEM768 + HAETAE2 | 266.0 | 484.0 | 530.7 |
| NTRU+ KEM768 + AIMer128f | 260.5 | 450.0 | 521.3 |

단위는 완료 핸드셰이크/초이며 세 블록의 중앙값이다. 이것은 연결·종료·기록 비용을 포함한 실험 서비스의 처리량이다. 클라이언트 수를 늘리면 처리량은 증가했지만 비례해서 증가하지는 않았다.

### 부하 중 배포 전환

첫 시험은 클라이언트 종료 오류로 실패했고 실패 기록을 보존했다. 오류 원문이 없어 그 실행의 정확한 원인은 확정하지 않았다. 이후 결과 기록 방식과 오류 진단을 개선하고 배포 항목만 재시험했다.

재시험에서는 클라이언트 4개가 73.76초간 24,504회 접속했다. 기존 서비스 3,847회, 승인된 신규 서비스 20,657회를 인증서로 구분했고 TLS 실패는 0회였다. 혼합 암호 후보는 거절하고 정상 후보로 전환했다. 이는 이 실행에서 실패를 관측하지 않았다는 뜻이다.

전환 후 이전 서버의 유휴 작업자가 `accept` 시간 초과로 종료되는 문제도 관측했다. 이 단계는 신규 서비스 전환을 보여줬지만, 이전 서비스가 즉시 복구 가능한 상태로 유지되는지까지 보장하지 않았다. 그 문제를 다음 실험에서 수정·검증했다.

자료: [네트워크·부하 결과](../../experiments/network-and-load/README.md).

## 9. 실험 4: 성능 측정을 배포 승인과 연결

암호 정책과 성능 기준을 함께 적용해 **암호 설정이 맞아도 서비스 응답 목표를 만족하지 못하면 배포를 거절**한다.

### 고정 도착률을 선택한 이유

동시 클라이언트가 응답을 기다렸다가 다음 접속을 보내면, 서버가 느려질수록 요청 발생률도 줄어든다. 최종 승인 시험에서는 0.1초마다 연결을 예약하는 초당 10회 고정 도착률을 사용했다. 늦거나 실패한 요청도 전체 시도 수에 포함했다.

각 후보는 100회씩 3구간, 총 300회다. 고정한 SLO (Service Level Objective)는 다음과 같다.

| 구간별 조건 | 기준 |
|---|---|
| 실패 비율 | ≤1% |
| 예정 시각부터 200ms 이내에 성공한 비율 | ≥99% |
| 성공 접속 완료 시간 p95 | ≤200ms |
| 부하 생성 지연 p95 | ≤50ms |

p95는 관측값의 95%가 그 값 이하인 백분위수다. 모든 구간이 조건을 만족해야 승인한다. 이 설계에서는 200ms 내 성공 99% 조건이 p95 조건보다 강하다. 서로 독립적인 세 가지 성능 효과를 입증한 것으로 설명하지 않고, 실패·기한·지연을 함께 기록하는 승인 규칙으로 설명한다. 부하 생성 지연은 클라이언트가 시험 일정을 제대로 지켰는지 확인하는 조건이다.

200ms는 관측된 결과에 맞춰 나중에 조정한 값이 아니라 실행 전에 정한 모의 목표다. Mac 에뮬레이션 전체 시험에서는 정상 후보도 100회 중 2회가 200ms를 넘어 거절됐다. 기준은 유지하고 네이티브 Linux 사전시험과 AWS 결과를 별도로 확인했다.

### 후보와 결과

지연 주입 후보는 암호 설정을 정상으로 유지한 채 서버 TLS 처리 전 350ms를 기다리게 했다. 최초 KPQC 배포 후보는 기존 고전 암호 서비스를 교체한다. 후속 업데이트 후보는 같은 SMAUG1 + HAETAE2로 인증서와 서버 프로세스만 갱신한다.

| 후보 | 암호 검사 | 세 구간 완료 시간 p95(ms) | 결과 |
|---|---|---|---|
| 지연 주입 후보 | 통과 | 382.56 / 382.46 / 381.96 | 거절 |
| 최초 KPQC 배포 후보 | 통과 | 32.99 / 33.19 / 33.28 | 승인 |
| 후속 업데이트 후보 | 통과 | 33.20 / 32.56 / 32.74 | 승인 |

세 후보 모두 TLS 연결은 각각 300회 성공했다. 하지만 지연 주입 후보는 기한과 지연 조건을 만족하지 못했다. 따라서 핵심 결과는 **연결 성공과 배포 승인을 실제로 구분했다**는 것이다.

이 표의 약 33ms는 순수 TLS 시간이 아니다. 같은 정상 후보의 구간별 `SSL_connect` p95는 약 5.51–6.03ms였고 별도 지표로 남겼다. 지연 주입은 클라이언트 핸드셰이크 대기에 반영되므로 해당 TLS 수치도 커진다.

## 10. 실험 5: 배포 후 장애 감지와 자동 복구

최초 KPQC 배포 이후 후속 업데이트까지 수행한 이유는 복구 대상을 고전 암호 서비스가 아닌 **이전 승인 KPQC 서비스**로 남기기 위해서다. 두 배포는 알고리즘 버전이 아니라 서비스 배포 이력이다.

1. 이전 승인 서비스를 복구 대상으로 유지한다.
2. 신규 배포 서비스의 서버 프로세스 그룹을 중단한다.
3. 실제 TLS 상태 확인에서 연속 두 번 실패하면 장애로 판정한다.
4. 이전 승인 서비스가 현재도 접속 가능하며 인증서·암호 정책이 맞는지 확인한다.
5. 활성 경로를 이전 서비스로 되돌리고 새 연결 성공을 확인한다.
6. 복구 후 고전 접속 거절과 암호 정책을 다시 검사한다.

장애 주입 대상은 **서버 EC2 내부의 신규 TLS 서비스 프로세스 그룹**이다. EC2 인스턴스·컨테이너 전체·TCP 라우터·가용 영역을 중단하지 않으며, 이전 승인 서비스는 같은 서버 EC2에 남아 있다. 따라서 이번 복구 시간은 서비스 프로세스 장애에 대한 결과이고, 인스턴스 또는 가용 영역 장애에 대한 고가용성 결과가 아니다.

과거에 정상이라는 기록만으로 복구하지 않는다. 다른 인증서, 오래된 상태 확인 결과, 고전 암호 복귀 요청도 거절하는지 시험했다. 유휴 작업자 종료 문제를 수정하고, 17초 유휴 후 작업자 8개와 정상 접속이 유지되는지 확인했다.

| 지표 | 결과 |
|---|---:|
| 장애 주입 요청부터 감지 | 1.596초 |
| 장애 주입 요청부터 첫 복구 성공 확인 | 2.951초 |
| 사전 복구 목표 | 10초 이내 |
| 장애 관측 시도 | 150회 |
| 신규 서비스 성공 | 23회 |
| 실패 | 21회 |
| 복구된 이전 서비스 성공 | 106회 |
| 마지막 20회 | 이전 서비스로 모두 성공 |

복구 시간에는 SSH 제어 왕복과 검증 과정이 포함된다. 21회 실패를 포함하는 장애 복구 결과이고 무중단이 아니다. 앞선 24,504회 실패 0회는 **정상 서비스 간 전환**, 이번 21회 실패는 **서비스를 중단한 뒤 복구**이므로 두 실험은 모순되지 않는다.

최종 전환·성능 승인·복구 검증은 24개 항목을 통과했다. 기존 암호 정책 게이트 63개도 같은 AWS 워크플로에서 통과했다.

## 11. CI/CD 실행과 증적 관리

CI (Continuous Integration)는 소스 변경 시 정책 함수와 자원 정리 실패 경로를 시험하고 Docker 이미지를 빌드해 로컬 통합 시험을 실행한다. 오류 후보를 거절하는 동작도 자동 검사한다.

수동 AWS 워크플로는 다음 순서를 자동화한다.

`소스 checkout → 이미지 빌드 → 로컬 사전시험 → AWS 단기 인증 → 기존 EC2 시작 → 동일 이미지 전달·확인 → 원격 시험 및 서비스 경로 전환 → 증적 저장 → 임시 SSH 규칙 제거·EC2 중지`

OIDC (OpenID Connect)는 GitHub 실행에 AWS 단기 권한을 부여하기 위한 인증 경로다. SSH는 서버·클라이언트 명령 실행 경로이고, 실제 측정 TLS는 두 EC2 사이에서 진행한다. 수동 시작은 자동화 부재가 아니라 실행 시점을 사람이 선택한다는 뜻이다. 이후 절차는 워크플로가 수행한다.

시험한 이미지를 AWS에 전달하고 이미지 식별자를 대조했다. 이는 시험한 이미지와 배포한 이미지가 동일한지 확인하는 절차다. 이미지 제작자의 진위, 의존성의 취약점 또는 빌드 전체의 공급망 안전성을 인증하는 절차는 아니다. 원기록, 후보 인증서 지문, 정책 식별자, 소스 커밋, 판정과 자원 정리 결과를 남겼다. EC2 두 대의 중지는 워크플로 대기 명령과 별도 AWS 조회로 확인했다.

최종 AWS 실행: [36032662708](https://github.com/17seetwice/kpqc-tls-devops-lab/actions/runs/36032662708), 실험 소스 `c232f7d`. 문서 공개 커밋 `489b7c9`의 [CI](https://github.com/17seetwice/kpqc-tls-devops-lab/actions/runs/36037680259)도 통과했다. 문서 수정 커밋이 실험 수행 소스와 같다고 표기하지 않는다.

## 실험 개요 및 주요 결과

본 실험은 국산 양자내성암호를 적용한 TLS (Transport Layer Security) 1.3의 성능을 측정하고, 실제 협상 결과와 응답 성능을 배포 승인 및 장애 복구 절차에 연결하는 것을 목적으로 한다. KPQC–OpenSSL Docker 이미지를 사용해 AWS EC2 서버·클라이언트 두 대에 각각 CPU 2개·메모리 512 MiB로 제한한 실험 컨테이너를 구성하였다. SMAUG·NTRU+ 키 교환과 HAETAE·AIMer 서명의 42개 조합 및 고전 암호 기준선을 대상으로 세션 재개 없는 전체 핸드셰이크를 측정하였다. 새 프로세스와 프로세스 재사용 조건의 실행 순서를 균형화하고, 대표 조합에 대해 MTU (Maximum Transmission Unit), 추가 네트워크 지연, HelloRetryRequest 및 동시 접속 조건을 비교하였다.

배포 검증에는 실제 키 교환·서명 식별자, 인증서 검증 결과, 금지된 접속의 거절 여부와 후보 증적의 일치 조건을 적용하였다. 또한 초당 10회의 고정 도착률 부하에서 접속 완료 시간과 성공률을 평가하여 성능 기준을 배포 승인 조건에 포함하였다. 정상 후보 두 개의 구간별 접속 완료 시간 p95는 약 32.6–33.3ms로 승인 기준을 충족한 반면, 350ms 지연을 주입한 후보는 TLS 연결에 성공했음에도 약 382ms의 p95를 보여 거절되었다. 이 지표는 접속 예정 시각부터 시험 클라이언트 종료까지의 시간이며, 별도로 측정한 순수 TLS 핸드셰이크 지연과 구분하였다.

신규 배포 서비스 중단 시험에서는 이전 승인 KPQC 서비스의 현재 연결·인증서·암호 설정을 확인한 뒤 활성 경로를 복구하였다. 장애 주입 요청부터 감지까지 1.596초, 첫 복구 성공 확인까지 2.951초가 소요되었으며, 장애 관측 구간의 150회 접속 시도 중 21회가 실패하였다. 기존 암호 정책 검증 63개와 전환·성능 승인·복구 검증 24개 항목을 통과하였다. 결과는 사전 배포한 신뢰 인증서와 제한된 자원·부하 조건에서, TLS 연결 성공 여부를 넘어 암호 적합성과 응답 성능에 근거한 배포 판단 및 KPQC 구성을 유지하는 자동 복구가 가능함을 보여준다.
