# 레거시→KPQC 전환·성능 게이트·복구 실험

## 목적과 사전 승인 조건

레거시 TLS 서비스에서 KPQC 서비스로 실제 활성 경로를 전환하고, 암호 적합성과 별개로 성능 조건을 판정한 뒤 배포 후 장애에서 이전 승인 KPQC 버전으로 복구한다. 기존 결과를 대체하지 않는 별도 실행이다.

`policies/release-slo.json`은 시험 전에 정한 모의 서비스의 응답 목표를 정의한다. 초당 10회 고정 도착률로 10초 × 3구간을 측정한다. 각 구간에서 접속 시도 실패율 ≤1%, 예정 도착부터 완료까지 200ms 내 성공 비율 ≥99%, 그 지연의 성공 표본 p95 ≤200ms를 요구한다. 부하 생성 지연 p95가 50ms를 넘으면 측정 부적합으로 승인하지 않는다. 누락·중복·잘못된 인증서·오래된 증적도 승인하지 않는다. 모든 시도를 보존하고 실패를 표본에서 숨기지 않는다.

## 시나리오

1. X25519 + ECDSA P-256인 초기 서비스를 실제 접속해 확인한다. 전환 가능한 클라이언트는 레거시와 KPQC를 지원한다고 가정한다.
2. KPQC 구성은 맞지만 TLS 서버에 350ms 처리 지연을 주입한 후보를 암호 검사에서는 통과, 성능 검사에서는 거절한다. 기존 레거시 경로 유지와 금지 후보 인증서 미노출을 확인한다. 이는 장애 주입에 대한 검출 시험이며 KPQC 자체가 느리다는 실험이 아니다.
3. 최초 SMAUG1 + HAETAE2 배포 후보를 동일 조건으로 검증하고 승격한다. 실제 관측 인증서와 협상 코드로 전환을 확인한다. 이후 레거시로의 rollback은 금지한다.
4. 후속 KPQC 업데이트 후보를 검증·승격하되 이전 승인 서비스를 복구 경로로 보존한다. 신규 배포 서비스의 서버 프로세스 그룹 중단을 주입하고, 자동 상태 관측에서 2회 연속 실패 시 이전 승인 서비스의 현재 정상 여부와 승인 이력을 확인한 후 복구한다. 복구 후 인증서·암호 정책·고전 접속 차단을 재검증한다.

## 측정과 한계

공개할 지연은 두 개다. (a) C 클라이언트 `SSL_connect` 구간의 TLS 지연, (b) 부하 생성기의 예정 도착부터 C 클라이언트 종료까지의 접속 시도 완료 지연. (b)는 스케줄 대기·프로세스 초기화·TCP·준비 신호·TLS·종료를 포함하며 성능 게이트에 사용한다. HTTP와 업무 거래는 포함하지 않는다. 실패율 분모는 예약된 전체 도착 수다. 지연 장애 동안에도 도착률을 줄이지 않는 open-loop 부하이며, 최대 동시 작업자 수와 생성 지연을 함께 기록한다.

장애 감지/복구 시간은 제어기 단조 시계의 동일 시간축에서 기록한다. 주입 요청부터 첫 복구 성공 확인까지를 10초 목표와 비교한다. 실패 연결이 발생할 것으로 예상하며 무중단을 주장하지 않는다. 기존 세션의 애플리케이션 거래 보존, 운영 PKI 체인, 자원 예측·메모리 격리, 전 알고리즘 최적 선택은 범위 밖이다.

기존 암호에서 KPQC로의 전환은 최초 배포 시 수행한다. 이후 장애가 발생하면 신규 배포 서비스에서 이전 승인 KPQC 서비스로 복구한다. 복구 정책은 서버에 저장된 이전 승인 버전만 허용하며, 임의의 고전 경로 선택을 허용하지 않는다. 제어기와 시험 호스트는 신뢰한다.

## 환경·실행·정리

로컬 smoke는 1구간 ×2초로 기능만 확인하고 동일 수치 결과로 합산하지 않는다. AWS는 기존 서울 EC2 두 대, 각 컨테이너 2 CPU/512MiB, 동일 이미지, 사설 TLS 연결을 사용한다. 현재 listener의 유휴 `accept` 시간 초과 시 작업자가 종료되는 문제를 먼저 수정하고 15초 이상 유휴 후 재접속 시험을 수행한다. 빌드·기존 정책 회귀·로컬 통합시험 후 원격 실행한다. 종료 시 성공/실패와 무관하게 컨테이너 정리·임시 SSH 규칙 제거·EC2 중지 및 별도 상태 확인을 수행한다.

새 결과는 먼저 사용자 검토용 문서에 기록하며 GitHub의 기존 결과표를 임의 교체하지 않는다. 연구실 내부 PDF·그림은 업로드 대상이 아니다.

## 검토 기록

- 사전 판정 검토: 모든 예정 시도를 분모로 사용하고, 누락·중복·오래된 증적·TLS 식별 불일치·부하 생성 지연은 승인하지 않는다.
- 로컬 smoke `local-release-20260924T170110Z`: 레거시 실접속, 17초 유휴 후 작업자 8개 생존, 느린 후보 암호 통과/성능 거절, 정상 두 차례 승격, 고전 롤백 금지, 장애 후 승인 KPQC 복구 통과. smoke의 20개/구간은 최종 AWS 성능 결과로 사용하지 않는다.
- 성공 판정은 장애 구간 실패 0회를 요구하지 않는다. 장애 주입 중 실패 시도는 별도 공개하고 마지막 20개 접속의 정상 복구를 확인한다.

- Mac amd64 에뮬레이션 전체 반복 `local-release-20260924T170605Z`에서 최초 KPQC 배포 후보의 첫 100개 중 2개가 200ms를 초과(317.545/271.876ms)하여 기한내99% 조건에 거절됐다. TLS 자체는300/300성공이며 다른 두 구간은 통과했다. 실패를 보존하고 SLO 수치를 변경하지 않는다. 환경 원인은 이 기록만으로 확정하지 않는다. GitHub 네이티브 Linux에서 전체 반복을 사전 검증한 뒤에만 AWS를 시작한다.

## 배포 후보의 역할과 실험 순서

**최초 KPQC 배포 후보**는 기존 X25519 + ECDSA P-256 서비스를 SMAUG1 + HAETAE2 서비스로 전환하기 위한 배포 대상이다. 암호·인증서 검증과 성능 기준을 통과하면 기존 서비스를 대체한다.

**후속 업데이트 후보**는 KPQC 도입 이후의 서비스 갱신을 모사한다. 동일한 SMAUG1 + HAETAE2를 사용하되 새로운 서버 인증서와 별도 서버 프로세스로 배포한다. 이번 실험에서 변경하는 것은 인증서와 배포 대상이며, 암호 알고리즘과 업무 기능은 변경하지 않는다.

후속 업데이트를 승인·배포한 다음 신규 배포 서비스에 장애를 주입한다. 최초 KPQC 배포로 승인받은 서비스가 이때의 **이전 승인 서비스**다. 해당 서비스의 현재 TLS 연결·인증서·암호 정책을 확인한 뒤 연결 경로를 복구한다. 두 단계는 **KPQC 최초 도입**과 **도입 후 갱신·장애 복구**를 각각 검증하며, 복구 후에도 KPQC 구성을 유지한다.
