# KPQC 기반 TLS 1.3 성능 측정 및 정책 기반 배포 검증

후속 실험은 [전환·성능 승인·복구 보고서](../after_claude/release/README.md)를 참조한다. 아래 내용은 초기 실험 기록이다.

기술보고서 개정안 · 사용자 검토용 · 2026-09-24

## 초록

본 실험은 국산 양자내성암호를 통합한 OpenSSL 환경에서 TLS (Transport Layer Security) 1.3 핸드셰이크 비용과 배포 후보의 암호 정책 적합성을 평가한다. SMAUG·NTRU+ KEM (Key Encapsulation Mechanism) 7개 파라미터와 HAETAE·AIMer 서명 6개 파라미터의 42개 조합을 고전암호 기준선과 함께 측정하였다. AWS (Amazon Web Services) 동일 가용 영역의 두 EC2 (Elastic Compute Cloud) 인스턴스에서 클라이언트 SSL_connect 시간, CPU (Central Processing Unit) 시간, 핸드셰이크 메시지 바이트 및 별도 실행의 최대 RSS (Resident Set Size) 증가량을 수집하였다. 배포 검증에서는 정상 후보의 승격과 암호 설정·증적 오류 후보의 거절을 시험하였다. 결과는 특정 구현 및 시험 환경의 관측값으로 제시한다.

## 1. 연구 질문

- RQ1. KEM·서명 구성과 프로세스 재사용 조건에 따른 TLS 연결 수립 비용은 어떻게 관측되는가?
- RQ2. 정상 접속과 제한된 클라이언트 프로브를 결합하여 후보의 정책 위반을 탐지할 수 있는가?
- RQ3. 후보 거절·승격·정리 과정에서 기존 활성 경로가 의도한 상태로 유지되는가?

RQ1은 순차 연결 성능을, RQ2–3은 배포 제어의 기능적 동작을 다룬다. 서버 용량 및 운영 SLA는 평가 범위에 포함하지 않는다.

## 2. 환경 및 방법

서버와 클라이언트는 서울 ap-northeast-2a의 m7i.large 각 1대이다. 사설 IPv4, Docker host network, MTU (Maximum Transmission Unit) 9001을 사용하며 컨테이너 한도는 CPU 2개와 512 MiB이다. TLS 1.3 및 TLS_AES_256_GCM_SHA384를 고정하고, 서버의 자체 서명 리프를 명시적으로 신뢰하며 호스트 이름을 검증한다.

KEM은 SMAUG1·3·5와 NTRU+576·768·864·1152, 서명은 HAETAE2·3·5와 AIMer128f·192f·256f이다. 기준선은 X25519 + ECDSA이다. 서로 다른 보안 파라미터를 포함하므로 동일 보안 수준의 알고리즘 비교로 해석하지 않는다.

시간 실험은 모드별 5라운드로 구성하고 라운드 내부의 구성 순서를 무작위화하였다. 새 프로세스 조건은 구성·라운드별 3회, 프로세스 재사용 조건은 준비 연결 2회 후 분석 연결 3회를 수행하였다. 두 조건 모두 매 연결 전체 핸드셰이크를 수행한다. 라운드 전후 기준선 감시 측정은 일반 집계에서 제외하였다.

| 지표 | 정의 | 집계 |
|---|---|---|
| 핸드셰이크 지연 | 클라이언트 SSL_connect 호출 전후 모노토닉 시간 차이 | 구성·모드별 15회 중앙값 |
| CPU 시간 | SSL 호출 전후 사용자·커널 CPU 시간의 합 차이 | 서버·클라이언트 분리 |
| 메시지 바이트 | TLS 핸드셰이크 메시지 콜백의 송수신 길이 | 방향별 기록 |
| 최대 RSS 증가량 | 초기화 이후 재설정한 최고 RSS 대비 SSL 호출 구간의 최고 기록 증가 | 별도 새 프로세스 3회 중앙값 |

TCP (Transmission Control Protocol) 연결 준비·HTTP (Hypertext Transfer Protocol)·파일 전송·연결 종료는 대표 지연 지표에서 제외한다. 메시지 바이트는 회선 전체 바이트가 아니다. RSS는 페이지 점유 지표이며 알고리즘의 총 할당량을 나타내지 않는다. 메모리 사전시험에서는 양 EC2에서 16 MiB 페이지 접근에 대응하는 증가를 확인하였다.

## 3. 배포 정책 및 구조

![배포 게이트](architecture/ko/fig1-architecture.png)

**그림 1. 정책 기반 후보 검증 및 활성 경로 전환.** 클라이언트는 TCP 라우터의 후보 경로로 접속하며, 관측 증적과 승인 정책의 비교 결과에 따라 승격 또는 기존 경로 유지가 결정된다. 시험용 라우터는 TLS를 종단하지 않는다.

정책은 TLS 버전, KEM, 서명, cipher suite, 인증서 검증 및 금지된 클라이언트의 접속 거절을 요구한다.  PQC (Post-Quantum Cryptography) 접속이 성공하더라도 고전 전용 접속이 허용되면 후보를 거절한다. TLS 1.2 프로브에는 별도 양성 대조를 둔다.

후보 세대·인증서·이미지·정책 식별자와 증적 시각을 대조하여 불일치 및 오래된 결과를 거절한다. 타임아웃·손상된 출력도 거절한다. 이 검증은 신뢰한 제어기의 실수와 결과 재사용을 다루며 악의적인 제어기에 대한 원격 증명은 아니다.

## 4. 결과

| 측정 | 고전 기준선 | PQC 구성별 중앙값 범위 |
|---|---:|---:|
| 새 프로세스 지연 | 1.388 ms | 3.503–11.287 ms |
| 프로세스 재사용 지연 | 0.538 ms | 2.403–10.529 ms |
| 클라이언트 최대 RSS 증가 | 460 KiB | 648–980 KiB |
| 서버 최대 RSS 증가 | 420 KiB | 628–1,252 KiB |

총 수집 연결은 1,935회이며 시간 분석 1,290회, 메모리 분석 129회, 준비·감시 연결 516회로 구성된다. 수집 연결의 세션 재개와 HRR은 모두 0회였다. 전체 그림과 구성별 값은 [결과 및 캡션](../after_claude/03_results.md)과 [요약 CSV](../after_claude/data/summary.csv)에 제시한다.

최종 AWS 게이트는 63/63개 검증 항목을 통과하였다. 활성 경로 관측 69회에서 실패는 없었다. 검증 항목 수는 성공한 TLS 연결 수와 다르며, 예상된 오류 후보 거절도 포함한다.

## 5. 실행 추적성 및 타당성

성능 기록은 `aws-extended-20260924T113201Z`, 최종 게이트 기록은 `aws-gate-20260924T114045Z`이다. 두 기록은 로컬 제어기가 AWS에서 실행한 결과이며, 서로 다른 실험 이미지 식별 정보를 보존한다. 기존 GitHub Actions 실행의 32항목 결과와 혼합하지 않는다. 원자료 해시·이미지 식별 정보는 공개 증적을 따른다. 당시 소스가 미커밋 상태였으므로 이후 문서 커밋을 실행 당시 커밋으로 소급하지 않는다.

단일 EC2 쌍, 순차 연결, 직접 신뢰한 리프 인증서, 커스텀 암호 식별자 조건의 결과이다. Cold 다음 warm의 고정 실행 순서 때문에 두 조건 차이에는 실행 시점 효과가 포함될 수 있다. 메모리는 구성별 3회 탐색적 측정이다. 알고리즘 보안 인증, 외부 상호운용성, 운영 용량 및 무중단 보장을 주장하지 않는다.

## 6. 후속 연구

모드 순서 무작위화 및 여러 실행의 재현성 확인을 우선한다. 이후 지연·MTU 조건, 동시 접속, 부하 중 전환, 인증서 체인을 평가한다. 현재 서버는 순차 처리이므로 동시 부하 실험 전에 서버 동시 처리 구조를 구현해야 한다. [상세 계획](../after_claude/05_future_experiments.md)은 완료된 결과와 구분하여 관리한다.

측정 용어·메모리 수치의 해석 및 미실행 계측 검증은 [측정 보완 문서](MEASUREMENT_NOTES.md)에 기록하였다. RSS 계수 오차와 계측 영향의 정량 검증은 아직 완료하지 않았으며, 메모리 값은 탐색적 관측으로 제시한다.
