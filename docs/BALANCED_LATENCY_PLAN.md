# 실행 순서 균형화 TLS 지연 실험

## 목적

기존 cold 이후 warm의 고정 실행 순서를 보완한다. 기존 두 EC2 (Elastic Compute Cloud) 인스턴스를 재사용하며 신규 인스턴스는 생성하지 않는다. TLS (Transport Layer Security) 계측 C 코드와 시간 경계는 유지한다.

## 설계

- 43개 구성: 기준선 1개 + KEM (Key Encapsulation Mechanism) 7개 × 서명 6개.
- 총 10개 짝지은 블록. Cold-first 5개, warm-first 5개의 순서를 seed 20260926으로 섞는다.
- 각 블록에서 구성 순서를 무작위화하되 cold/warm 사이에는 같은 순서를 사용한다.
- 모드별 블록 앞뒤 기준선 감시 측정을 추가한다.
- Cold는 구성별 3회, warm은 준비 2회 + 분석 3회. 각 구성·모드에서 총 30회 분석한다.
- 예상 수집 3,600회, 분석 2,580회. 메모리 실험은 이번에 반복하지 않는다.
- 실행 순서·블록 시각·커밋·이미지 식별자를 저장한다. 양쪽 협상·인증서 검증·재개 없음·HRR (HelloRetryRequest) 0·메시지 바이트 대응을 확인한다.

## 실행 및 분석

GitHub Actions 수동 워크플로의 `balanced_latency=true`로 실행한다. Runner에서 이미지 빌드·게이트 시험·축소된 지연 수집 시험을 먼저 수행한다. 이어 AWS 권한 취득, EC2 시작, 동일 이미지 전달, 게이트 시험, 전체 지연 실험, 증적 저장 및 EC2 중지를 수행한다. 기존 SSH (Secure Shell) 규칙은 소유권을 취하지 않으며 해당 실행이 추가한 규칙만 정리한다.

구성·모드별 30회 중앙값과 각 블록의 3회 중앙값을 보고한다. 모드 차이는 같은 블록의 중앙값끼리 짝지어 확인하고 시작 순서별 결과도 점검한다. 기존 실행과 이번 실행을 합쳐 표본 수를 늘리지 않는다.

이 설계는 한 EC2 쌍에서 수행하는 한 번의 실행이다. 여러 날짜·독립 인스턴스 반복, 동시 부하, 네트워크 조건 변화, RSS (Resident Set Size) 계수 정확도 검증을 대신하지 않는다. 후속 결과는 수집·검토 후 기존 결과와 별도로 제시한다.
